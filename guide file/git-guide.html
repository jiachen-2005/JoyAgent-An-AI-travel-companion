短命分支工作流Short-Lived Branch Workflow

01为什么要这样做Why

我们之前有 frontend 和 backend 两条长期分支,各写各的。问题是它们永远不会自己合并——等到要联调时才发现前端对着旧接口在写,后端的字段早改名了。而 git 这时候一个冲突都不会报,因为两边改的是不同文件。合并"成功"了,跑起来却全是 undefined。

短命分支反过来:写完一个功能就合回 main。集成不再是学期末的一场灾难,而是每天的一件小事。任何人问"现在做到哪了",答案永远是"你看 main"。

We used to keep two long-lived branches, frontend and backend, each going its own way. They never merge on their own — by integration time the frontend is built against an old API and the backend has renamed half its fields. And git reports zero conflicts, because the two sides edited different files. The merge "succeeds" and the app is full of undefined.

Short-lived branches invert this: finish a feature, merge it back into main. Integration stops being an end-of-semester disaster and becomes a daily non-event. Whenever anyone asks where we are, the answer is always "look at main".

一个功能,一条分支 One feature, one branch.
写完就合回 main Merge back as soon as it's done.
main 永远能跑 main always runs — everything goes through a PR.

02怎么用How

1从最新的 main 切分支 Branch off the latest main

先拉 main,再切分支。顺序反了会带着旧代码开工。

Pull first, then branch — the other order starts you from stale code.

git switch main
git pull
git switch -c feat/be-trip-crud     # -c = 新建并切过去 / create and switch

2干活,小步提交 Work, commit in small steps

不用等全部写完才提交。写完一个能跑的小块就提交一次。

Don't wait until everything is done — commit whenever a small piece works.

git add .
git commit -m "feat(trips): add trip creation endpoint"

如果这个功能做了好几天,中途 git fetch origin && git merge origin/main 同步一下,免得后面冲突堆太多。
If the feature takes several days, run that once in a while so conflicts don't pile up.

3推上去,开 PR Push and open a PR

推完 GitHub 会出现一个 "Compare & pull request" 按钮,点它。描述里写清楚做了什么和怎么验证。

After pushing, GitHub shows a "Compare & pull request" button — click it. Say what you did and how to verify it.

git push -u origin feat/be-trip-crud

4合并,然后删掉分支 Merge, then delete the branch

在 GitHub 上点 Squash and merge——它把你的十几个 commit 压成一个,main 的历史才干净。远端分支会自动删除,本地再清理一下。

Click Squash and merge — it collapses your dozen commits into one, keeping main's history clean. The remote branch is deleted automatically; clean up locally.

git switch main
git pull
git branch -d feat/be-trip-crud     # 删掉本地那条 / delete the local one

03分支怎么命名Naming

格式 类型/领域-描述,描述用小写英文加连字符。
类型:feat 新功能 · fix 修 bug · chore 配置工具 · docs 文档 · spike 试验(可以不合并直接删)
领域:be 后端 · web 前端 · mob 移动端 · llm LLM 层 · api 外部 API · infra Docker/CI

Format type/scope-description, lowercase and hyphenated.
Types: feat new feature · fix bug fix · chore tooling · docs docs · spike experiment (fine to delete unmerged)
Scopes: be backend · web web · mob mobile · llm LLM layer · api external APIs · infra Docker/CI

feat/be-contracts-schemas          fix/be-jwt-refresh-expiry
feat/llm-itinerary-prompt          chore/infra-docker-compose
feat/api-google-places-adapter     spike/llm-structured-output
feat/web-itinerary-timeline

04速查Cheat sheet

# 开始一个新功能 / start a new feature
git switch main && git pull
git switch -c feat/be-something

# 干活 / work
git add . && git commit -m "feat(scope): what you did"

# 交出去 / hand it in
git push -u origin feat/be-something
# 然后去 GitHub 开 PR → Squash and merge

# 收尾 / wrap up
git switch main && git pull
git branch -d feat/be-something

# 我现在在哪条分支? / which branch am I on?
git status

只记一句的话:从 main 切一条分支,功能写完就合回 main,合完删掉。

If you remember one thing: branch off main, merge back when the feature is done, delete the branch.
